# Проверка отправителя: разбор безопасности (0.8.13)

Разбор диффа `q/trust` по двум вопросам: можно ли подделать подтверждение отправителя и можно ли вызвать запрос DNS к чужому домену. Ответ — нет и нет; ниже, как это устроено.

## Можно ли подделать подтверждение

Подтверждение даёт лестница доказательств (`crates/depesha-core/src/sender.rs`), и каждая её ступень опирается на то, что видел письмо целым.

### Ступени 1 и 2 — слово сервера ящика

Сервер ящика верится только когда он сам ставит свой `Authentication-Results` сверху и вырезает чужие копии: Gmail, Яндекс и Mail.ru по IMAP, Exchange Online по EWS (`avatar.rs::Receiver::vouches`). Чужой `Authentication-Results` не верится никогда — это решение #35, оно осталось в силе.

Сервер говорит «отправитель подтверждён», когда:

- `dmarc=pass` за домен `From` (ступень 1), или
- прошедший `dkim=`/`spf=` за организацию `From` без `dmarc=` (ступень 2, 2.1 Б).

Риск ступени 2: сервер мог прочитать `From` иначе, чем приложение. Закрыт тем, что письмо должно иметь один `From`, и оба читателя заголовков должны видеть его одинаково (`message::sole_from`). Письмо с двумя `From` не подтверждается ничем (`Reason::AmbiguousFrom`).

Риск подделки самого `From`: подпись организации `From` требует настоящего письма этой организации. Подделка адреса без закрывающего ключа не проходит.

Риск «сервер проверил не то тело»: хэш тела считал сервер при приёме, по исходным байтам. Приложение проверить это позже не может, но и не должно: то, что видел сервер, и есть доказательство.

### Ступень 3 — своя полная проверка

Проверка собрана по RFC 6376 §3.7 из публичных частей `mail-auth`. Это канонические заголовки по списку `h=`, заголовок `DKIM-Signature` без значения `b=`, и **хэш тела** — сырые байты, а не их base64. Подпись проверяется ключом из DNS.

Прежняя проверка шла через `verify_dkim` библиотеки, и та **не добавляет хэш тела к подписанным данным**. Из-за этого она отвергала подписи настоящих отправителей: подпись по RFC, сделанная сторонним кодом, не проходила `verify_dkim`. Теперь подпись проверяется правильно, а тесты ядра подписывают письма своим ключом по RFC.

Отвергается: `a=rsa-sha1` (RFC 8301), `l=` (длина тела), ключ в режиме проверки `t=y` (RFC 6376 §3.6.1), `i=` чужого домена, `x=` истёк. Отвергается и подпись, которая не покрывает `From` или покрывает больше 64 заголовков, и `adkim=s`, требующий точного имени.

### Ступень 4 — подпись по исходным заголовкам Exchange

Письмо пришло через Exchange в своей сети: тело собрано заново, поэтому проверяется подпись по **исходным** заголовкам (`0x007D`), без хэша тела.

Что здесь может сломаться и как закрыто:

- **Подмена тела.** Подпись покрывает только заголовки, тело не покрыто. Тот, у кого есть настоящее подписанное письмо на этот же ящик, может подменить тело. Поэтому на этой ступени **нет логотипа**: знак подлинности должен стоять на полной проверке. Ущерб — отправитель узнает, что тело прочитано (принятый риск в `docs/acceptance.md` 4.4).
- **Повтор письма.** Подпись письма, посланного давно, не должна подтверждать письмо, пришедшее сейчас. Требования: подпись должна покрывать тот заголовок, в котором стоит адрес ящика (`To` или `Cc`). Время письма (`t=` подписи или **подписанный** `Date`) должно быть близко к времени получения — предел сутки. `Date`, который никто не подписал, временем письма не считается.
- **Ключ чужого домена.** DNS спрашивается только про `d=` подписи, совпадающий с организацией `From`; подпись чужой организации отбрасывается до сети.

## Можно ли вызвать запрос DNS к чужому домену

Нет. Все имена, которые спрашиваются, выводятся из организации `From` или из домена логотипа:

| Имя | Откуда | Когда |
| --- | --- | --- |
| `<selector>._domainkey.<d=>` | `d=` подписи, совпадающий с организацией `From` | своя проверка |
| `_dmarc.<домен From>` и `_dmarc.<организация>` | домен `From` | `adkim=s` |
| `_dmarc.<домен>` и `default._bimi.<домен>` | регистрируемый домен адреса `From` | логотип |

Подпись чужой организации отбрасывается **до** сети: `dkim.rs::candidates_for` оставляет только подписи, у которых `d=` выровнен с доменом `From`. Тест `a_signature_of_another_organization_asks_no_dns` проверяет, что для письма с подписью `d=t.tracker.example` DNS не спрашивается вовсе (`asked() == 0`).

Имя `d=` может быть поддоменом организации `From` (`mg.bank.ru` для `bank.ru`) — это принятый риск: организация отдала поддомен третьей стороне, и та подписывает письма от имени организации. Он записан в `docs/acceptance.md` 4.4.

## Переключатель «доверять по адресу»

Риск: подделка адреса доверенного отправителя получает картинки. Переключатель выключен по умолчанию, логотипа не даёт никогда, а явное «нет» сервера (`dmarc=fail`, `dkim=fail`) не перебивает. Строка над письмом говорит честно, что адрес не проверен. Запись в `docs/acceptance.md` 4.4.

## Что осталось за рамками

- **DNS без DNSSEC.** Тот, кто подменяет ответы DNS в сети пользователя, может подтвердить поддельное письмо. Принятый риск.
- **Шаг 4: тело не покрыто подписью.** Подделка тела настоящим подписанным письмом на тот же ящик. Принятый риск.
- **Сервер, который верит чужим копиям `Authentication-Results`.** Такой сервер не в списке доверенных, и приложение проверяет подпись само.
