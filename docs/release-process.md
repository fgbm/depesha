# Как готовится выпуск Депеши

Документ описывает путь версии от набора задач до опубликованного релиза. Он для владельца продукта и для агентов, которые делают макеты, тесты и код. Образцы: макеты и решения 0.6.0 (`design/mockups/0.6.0/`), макеты и опрос 0.7 (`design/mockups/0.7/`).

## Схема этапов

0. Сбор milestone: что входит в версию и какая у неё тема.
1. Разведка и технические спайки: что вообще возможно и сколько это стоит.
2. Макеты: варианты интерфейса для задач с UI/UX.
3. Сверка макетов со спайками: вычеркнуть невозможное, сузить раздутое.
4. Опрос тестировщиков в Telegram: вопросы вкуса и поведения.
5. Фиксация решений: `decisions.md`, правка макетов, отложенное — в issues.
6. Тесты, затем реализация, затем приёмка.
7. Выпуск: версия, тег, сборка и публикация, закрытие milestone.

Этапы 1 и 2 идут параллельно. Этапы 2–5 нужны только задачам с интерфейсом; задача без UI идёт с этапа 1 сразу на этап 6.

## 0. Сбор milestone

**Вход.** Открытые issues (`gh issue list`), раздел «Вне …» и отложенное из `decisions.md` прошлых версий, `PAPERCUTS.md`, раздел «Ещё не сделано» в `docs/ux.md`.

**Что делается.** Каждой задаче-кандидату даётся оценка размера (`size:S`…`size:XL`, см. ниже). Отмечаются связи: что от чего зависит, что удобно делать вместе (одна сущность, один экран, общий модуль). Из крупных связанных задач складывается тема релиза в одну фразу — она пойдёт во вступительный пост опроса и в описание выпуска. В GitHub создаётся milestone с номером версии (`0.7`, `0.6.2`), к нему привязываются выбранные issues. Что не влезает, остаётся в резерве: issues без milestone. Если кандидат был только строкой в `decisions.md` или `PAPERCUTS.md`, на него заводится отдельный issue.

**Артефакт.** Milestone в GitHub со списком issues и метками размера; тема релиза.

**Кто решает.** Владелец.

Оценки задач — метки размера в GitHub, они ставятся при сборе milestone: `size:S` — меньше дня, `size:M` — 1–3 дня, `size:L` — 3–7 дней, `size:XL` — больше недели (кандидат на разбиение). Рядом с меткой у задачи есть оценка в днях: при каждом расширении задачи (новая находка, довесок от соседней) сравнивается «было / стало», а версия, выросшая больше чем на 30% от исходной, — повод предложить владельцу, что перенести в следующую.

## 1. Разведка и технические спайки

**Вход.** Issues milestone.

**Что делается.** Для каждой задачи с интерфейсом выясняются конвенции макетов (раздел 2) и текущее устройство экрана в коде. Рискованные задачи — новые зависимости, поведение платформы, протокол сервера — прототипируются параллельно с макетами: в `/tmp` или в отдельном git worktree, без изменений в основном рабочем дереве. Спайк отвечает на конкретный вопрос: работает ли это на Linux (WebKitGTK), Windows и macOS, что запрещает платформа или сервер, сколько весит зависимость в сборке, какой объём работы на самом деле. Если поведение можно проверить только в настоящем WebKitGTK, это делается вручную через `npm run tauri dev` (WebKitGTK вне Tauri без GPU страницы не грузит, см. `e2e/README.md`). Для задач, зависящих от платформы, — значка в трее, уведомлений, движка webview — спайк идёт до макета, и его выводы входят в ТЗ автора макета: иначе макет нарисует то, чего платформа не умеет.

**Артефакт.** Короткая записка по спайку: факты, ограничения платформ, вес, оценка объёма; нужна ли ручная проверка на платформах при приёмке. Код спайка в репозиторий не попадает, а записка лежит в `design/mockups/<версия>/spikes/NN-тема.md`.

**Кто решает.** Исполнитель спайка докладывает факты; продолжать ли задачу — владелец.

## 2. Макеты

**Вход.** Issues с UI/UX, итоги разведки.

**Что делается.** Макеты лежат в `design/mockups/<версия>/NN-тема.html`: один самодостаточный HTML-файл на группу связанных issues (в 0.7: `01-background-notifications.html` на #4 и #63, `03-markdown-editor.html` на #45 и #44). Правила:

- Цвета, шрифты и размеры — переменные из `src/app.css` и стили компонентов, данные вымышленные.
- Светлая и тёмная темы.
- Кадры пронумерованы и имеют якоря `#s1`, `#s2`…; где есть выбор, рядом варианты А/Б/В с заметками, чем они различаются.
- Интерактив — там, где это дёшево (например, «Попробуйте: запись сочетания» в `05-keybindings.html`).
- Рекомендации автора макета помечаются классом `.rec` (метки «рекомендую», выделения), чтобы для опроса скрывать их одним правилом CSS.
- В конце файла — «Открытые вопросы к оператору» (якорь `#q`); у вопросов своя нумерация прямо в HTML, и в сводках владельцу используется она же — он отвечает по HTML.

Рядом `index.html` — оглавление: файлы, issues со ссылками, список кадров со ссылками на якоря, ссылка на milestone. Пока вариант не выбран, UI не реализуется.

**Артефакт.** `design/mockups/<версия>/*.html` и `index.html`.

**Кто решает.** Варианты готовит исполнитель, выбор — этапы 4–5.

## 3. Сверка макетов со спайками

**Вход.** Макеты и записки спайков.

**Что делается.** Из макетов вычёркиваются варианты, которые невозможны на одной из платформ или у сервера (например, кадр «Linux без области значков» в 0.7 появился из ограничения GNOME). Задачи, которые в макетах разрослись относительно issue, сужаются до issue; лишнее уходит в отдельные issues без milestone или в резерв. Здесь же сверяется объём версии: каждой задаче — оценка в днях, при расширении сравнивается «было / стало», и релиз, выросший больше чем на 30%, — повод предложить владельцу, что перенести в следующую версию.

**Артефакт.** Поправленные макеты, новые issues на отрезанное.

**Кто решает.** Владелец.

## 4. Опрос тестировщиков в Telegram

**Вход.** Макеты после сверки, открытые вопросы из них.

**Что делается.** Из открытых вопросов отбираются только вопросы вкуса и поведения, 8–12 штук. Технические и продуктовые вопросы в опрос не идут — их решает владелец. Опрос оформляется в `design/mockups/<версия>/poll.md` (образец — `design/mockups/0.7/poll.md`):

- Вступительный пост: тема версии, сколько опросов, срок.
- На каждый вопрос: картинки (с указанием файла макета и кадра), при необходимости пост с пояснением, затем опрос.
- Ограничения Telegram: вопрос до 300 символов, вариант до 100 символов, до 10 вариантов.
- Картинки кадров собирает `scripts/poll-shots.mjs` (снимок кадра светлой темы, заметки `.rec` и подписи скрыты) под номером вопроса (`01-close-a.png`); в репозитории PNG не лежат.
- Опросы не анонимные (чтобы переспросить «почему»), один ответ, если не сказано иное, срок около 3 дней.
- Последний вопрос — приоритеты релиза, несколько ответов.
- В конце `poll.md` — что вернуть после опроса: счёт голосов и заметные комментарии.

Голоса — совет, не приказ.

**Артефакт.** `poll.md`, картинки в `poll/`, итоги опроса.

**Кто решает.** Состав вопросов и публикация — владелец.

## 5. Фиксация решений

**Вход.** Макеты, итоги опроса, ответы владельца на технические вопросы.

**Что делается.** Решения записываются в `design/mockups/<версия>/decisions.md` по образцу `design/mockups/0.6.0/decisions.md`: заголовок, строка «Согласовано с оператором <дата>», раздел «Общие» (с тем, что вне версии), затем раздел на каждый issue — по пункту на решение со ссылкой на кадр и вариант («кадр 3, вариант В»). Где был опрос, у решения стоит счёт голосов. Отклонённый вариант упоминается, если причина неочевидна. Макет правится под выбранный вариант. Всё отложенное заводится отдельными issues. Макеты и `decisions.md` коммитятся (образец — коммит `chore: макеты 0.6.2 и решения по ним`), черновики не удаляются: по ним видно, из чего выбирали.

**Артефакт.** `decisions.md`, поправленные макеты, issues на отложенное.

**Кто решает.** Владелец.

## 6. Тесты, затем реализация, затем приёмка

**Вход.** `decisions.md`, макеты, записки спайков, issue.

**Тесты и код.** По каждой задаче сначала пишутся тесты по зафиксированному решению, потом код. Виды тестов в проекте:

- юнит-тесты Rust (`cargo test -p depesha-core`, `cargo test -p depesha --lib`) и фронтенда (`npx vitest run`);
- интеграционные тесты ядра против GreenMail и Dovecot в Docker (`crates/depesha-core/tests/greenmail.rs`, `dovecot.rs`; запускаются с `DEPESHA_IT=1`); причуда сервера получает тест, который её воспроизводит, или сценарный сервер вроде `tests/exchange_smtp.rs`;
- E2E: настоящее приложение на Xvfb под WebDriver (`e2e/run.mjs`, настройка в `e2e/README.md`).

Новые строки интерфейса — через `t()`/`tn()` на английском и русском (`CONTRIBUTING.md`). Коммиты — Conventional Commits с описанием по-русски; заголовок пишется для читателя страницы релиза, потому что из коммитов собираются заметки к выпуску. Перед коммитом работает хук персональных данных (`scripts/hooks/pre-commit`): включается один раз через `git config core.hooksPath scripts/hooks`, шаблоны лежат вне репозитория (`~/.config/depesha/private-patterns`) и в историю не попадают.

**Параллельные агенты.** Каждый работает в своём git worktree, а не в общем рабочем дереве: был случай, когда `git add -A` одной сессии унёс в origin чужие незаконченные файлы. Исполнители — дешёвые агенты: `coder` для кода, `explore` для поиска и сверки; дорогой `general` берут только для широкого исследования, а оркестратор сам руками не работает. Грабли из `PAPERCUTS.md`:

- `git worktree add` — всегда с абсолютным путём, иначе worktree окажется внутри основного checkout.
- Пустой `target/` в новом worktree собирается с нуля десятки минут; копировать прогретый: `cp -a --reflink=auto <основной>/target <wt>/target`.
- `node_modules` в worktree — симлинк на общий; пакеты ставить в основном checkout, иначе npm превратит симлинк в папку. Перед коммитом смотреть `git diff --cached --stat`, а не делать `add -A` вслепую.
- Контейнеры GreenMail/Dovecot общие на машину (`name: depesha` в `compose.test.yaml`); `docker compose … --force-recreate` ломает тесты соседней сессии. Перед пересозданием смотреть `docker ps` и `pgrep -af "e2e/run.mjs|WebKitWebDriver"`; занятые чужим прогоном контейнеры не трогать.
- Параллельно не больше 2–3 сборок Rust за раз, `CARGO_BUILD_JOBS=4`: иначе машина уходит в swap.
- Перед проверкой своей части сверять `git diff --name-only` со своим списком файлов; чужие правки перед коммитом прогонять хотя бы через `cargo fmt --all --check`, лучше `scripts/check.sh --fast`.
- Не перезаписывать чужие baseline метрик и инвариантов без нужды.
- Фоновые процессы останавливать по PID, а не `pkill -f <шаблон>`: шаблон совпадает с командной строкой самой оболочки.
- После отчёта исполнителя сверять `git log` и `git status` ветки — что коммитов и правок ровно столько, сколько ждали.

Issues для контекста читать через `gh issue view N --json title,body,comments`: `--comments` здесь молча пуст. Перед отчётом владельцу «готово» дешёвый read-only агент сверяет ветку с `decisions.md` и критериями, а отклонения выносит владельцу. Основное дерево — только для слияний: всякая другая работа, включая посторонние сессии, идёт в отдельном worktree или каталоге.

**Приёмка: автоматические проверки.** Локально перед коммитом `scripts/check.sh --fast`: rustfmt, clippy с `-D warnings`, `svelte-check --fail-on-warnings`, eslint, `scripts/frontend-metrics.sh`, `scripts/frontend-invariants.sh`, vitest, `cargo test`. Изменения в синхронизации, IMAP или SMTP требуют полного `scripts/check.sh`: он добавляет интеграционные тесты против GreenMail и Dovecot и E2E. Изменения в `src-tauri/src/updater.rs` или в release-процессе требуют `scripts/test-update.py` (две подписанные AppImage с одноразовым ключом: подписанное обновление ставится, подменённое отвергается).

Метрики и инварианты фронтенда сравниваются с baseline (`docs/frontend-metrics-baseline.txt`, `docs/frontend-invariants/`). Если рост оправдан, baseline перезаписывается `scripts/frontend-metrics.sh --save` и `scripts/frontend-invariants.sh --save` отдельным коммитом с объяснением в теле (образец — `chore: baseline метрик фронтенда после 0.6.2`).

CI (`.github/workflows/ci.yml`) запускается на push в `main` и на pull request, четыре задачи:

- **check** — те же проверки, что `scripts/check.sh --fast`, плюс `npm run build`;
- **integration** — интеграционные тесты против GreenMail и Dovecot;
- **e2e** — сборка с `--features e2e` и `e2e/run.mjs` на Xvfb с разблокированной связкой ключей; скриншоты шагов выкладываются артефактом `e2e-screens`;
- **build** — пакеты под Ubuntu, Windows и macOS (без артефактов обновления: ключ подписи есть только у релиза) и юнит-тесты ядра на каждой ОС.

**CI после push.** После каждого push в `main` прогон на GitHub проверяется сразу: `gh run list --repo fgbm/depesha --branch main --limit 3`, затем `gh run watch <id> --repo fgbm/depesha --exit-status` по запускам на новом коммите. Красный CI — блокер следующего слияния: пока он не позеленел, в `main` ничего нового не вливается. Локальный `scripts/check.sh` не заменяет CI: на машине стоят пакеты, которых может не быть на раннере.

**Приёмка: критерии.** `docs/acceptance.md` — критерии приёмки 1.0 с пометками **[обяз.]**/**[жел.]** и способом проверки (авто, Exchange, ручн., CI). Новое поведение версии добавляется туда строкой критерия в нужный раздел (так в 0.6.x появились 4.13 и 4.14). Там же сценарии ручной приёмки на Exchange 2019 (EWS и OWA) и входа через Google, Яндекс и Microsoft — их прогоняют, если задача задевает эти места. `docs/acceptance-report.md` — отчёт о прогоне критериев; он обновляется на каждом минорном выпуске (0.7.0, 0.8.0), а на патчах — нет (последний полный — на 0.2.0 с дополнениями до 0.5.0).

**Ручная проверка на платформах.** Если записка спайка требует, поведение проверяется руками на нужных ОС (`npm run tauri dev` или пакеты из артефактов CI-задачи build). Результат фиксируется комментарием в issue задачи.

**Артефакт.** Коммиты в `main` с тестами и кодом, зелёный CI, обновлённые критерии в `acceptance.md`, при необходимости новые baseline.

**Кто решает.** Готовность задачи — по зелёным проверкам и критериям; спорное по поведению — владелец. Pull request и ревью не нужны: разработчик один. Коммиты идут прямо в `main`; параллельная работа — в отдельном worktree, слияние через rebase и fast-forward.

## 7. Выпуск

**Вход.** Все issues milestone закрыты или перенесены, CI на `main` зелёный.

**Поднятие версии.** Один коммит `chore: версия X.Y.Z`. Номер меняется в шести файлах (по коммитам 0.6.3 и 0.6.4):

- `Cargo.toml` (версия workspace);
- `src-tauri/Cargo.toml` (зависимость `depesha-core = { version = … }`);
- `Cargo.lock`;
- `package.json`;
- `package-lock.json` (два места);
- `src-tauri/tauri.conf.json`.

Все шесть файлов перечислены в `CONTRIBUTING.md`. Тело коммита — сводка выпуска, несколько предложений по-русски для пользователя (образец — `chore: версия 0.6.0`); она становится первым абзацем заметок к выпуску. Без тела сводки не будет (так вышло у 0.6.2). Файла CHANGELOG нет.

**Картинки и текст описания.** Макеты (HTML) хранятся в репозитории, PNG — нет. Картинки опроса собирает `scripts/poll-shots.mjs`. Картинки к описанию релиза снимает `scripts/release-shots.sh` (сценарий `e2e/release-shots.mjs`): настоящее приложение на Xvfb поверх демо-данных `demo-seed`, кадры в `/tmp/depesha-release-shots/`; набор кадров правится под версию. Картинки к описанию релиза прикладываются к самому релизу на GitHub; в репозитории — только текст описания `docs/releases/<версия>.md`. Имена файлов кадров — только латиница: GitHub при загрузке вырезает кириллицу из имён, `01-фон-и-запуск.png` превращается в `01-.-.-.png`.

**Тег и сборка.** Коммит помечается тегом `vX.Y.Z`, тег пушится. Push тега `v*` запускает `.github/workflows/release.yml`:

- задача **release** собирает через `tauri-apps/tauri-action` четыре сборки: Ubuntu, Windows, macOS aarch64 и macOS x86_64; артефакты обновления подписываются ключом из секретов `TAURI_SIGNING_PRIVATE_KEY`, в сборку зашиваются OAuth-клиенты из секретов `DEPESHA_*_CLIENT_*`; всё складывается в черновик релиза «Депеша vX.Y.Z» вместе с `latest.json`;
- задача **publish** запускается, только если все четыре сборки прошли: `scripts/release-notes.sh` собирает заметки (сводка из тела коммита версии, затем коммиты с прошлого тега по группам «Новое», «Исправления», «Производительность», «Переработка», «Документация», «Служебное»), и `gh release edit` публикует релиз как последний. Установленные копии видят обновление через `releases/latest/download/latest.json` только после публикации.

Если сборка упала, черновик остаётся для разбора руками. Следить за прогоном — `gh run view` с повторами, а не по коду выхода `gh run watch` (обрывается на сетевой ошибке). Сборки не подписаны кодом: SmartScreen и Gatekeeper предупредят при первом запуске.

**Закрытие milestone.** В GitHub milestone закрывается после публикации. Автоматики для этого нет: milestone закрывается вручную последним шагом выпуска (в 0.6.2 его оставили открытым без открытых задач). Все фиксы между минорными версиями идут в ближайший минорный релиз, если владелец не просит патч.

**После выпуска.** Если версия меняла фронтенд, baseline метрик фронтенда обновляется отдельным коммитом (образец — `chore: baseline метрик фронтенда после 0.6.2`).

**Артефакт.** Коммит версии, тег, опубликованный релиз с пакетами и `latest.json`, закрытый milestone.

**Кто решает.** Владелец: когда выпускать и текст сводки.

## Чек-лист готовности к выпуску

- [ ] Все issues milestone закрыты или перенесены в следующий milestone / резерв.
- [ ] По задачам с UI есть `decisions.md`, реализация совпадает с выбранными вариантами.
- [ ] Отложенное из `decisions.md` и спайков заведено отдельными issues.
- [ ] Новое поведение описано критериями в `docs/acceptance.md`.
- [ ] CI на последнем коммите `main` зелёный: check, integration, e2e, build под три ОС.
- [ ] Если трогали синхронизацию, IMAP или SMTP — пройден полный `scripts/check.sh`.
- [ ] Если трогали обновление или release.yml — пройден `scripts/test-update.py`.
- [ ] Если задевали Exchange или OAuth — пройдены соответствующие ручные сценарии из `docs/acceptance.md`.
- [ ] Ручная проверка на платформах, которую потребовали спайки, сделана.
- [ ] Baseline метрик и инвариантов фронтенда соответствует дереву (`scripts/frontend-metrics.sh` и `scripts/frontend-invariants.sh` без регрессий).
- [ ] Коммит `chore: версия X.Y.Z` меняет все шесть файлов, в теле — сводка выпуска по-русски.
- [ ] Тег `vX.Y.Z` запушен, обе задачи release.yml прошли, релиз опубликован и помечен последним.
- [ ] Milestone закрыт вручную — последним шагом выпуска.
