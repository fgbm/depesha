# Критерии приёмки Депеши 1.0

Версия 1.0 принимается, когда выполнены все критерии с пометкой **[обяз.]**. Пометка **[жел.]** — по желанию, не блокирует выпуск. В колонке «Проверка» указано, как подтверждается критерий: **авто** — автотест против GreenMail в CI (`compose.test.yaml`), **Exchange** — ручной прогон на живом Exchange 2019, **ручн.** — ручная проверка на любом сервере.

Целевые серверы: Exchange 2019 (on-premises), Яндекс Почта, Mail.ru, Gmail (пароль приложения), Timeweb, Dovecot/Postfix. OAuth2 в 1.0 не входит.

## 1. Учётные записи

| № | Критерий | Проверка |
| --- | --- | --- |
| 1.1 | **[обяз.]** Мастер добавления: адрес и пароль, затем автоопределение серверов. Порядок: известные провайдеры → autoconfig (`autoconfig.<домен>`, ISPDB Thunderbird) → SRV (`_imaps._tcp`, `_submission._tcp`) → перебор `mail.<домен>`, `imap.<домен>`, `smtp.<домен>` на 993/143 и 587/465. Найденные параметры показываются, их можно исправить вручную. | ручн., авто (перебор) |
| 1.2 | **[обяз.]** Перед сохранением мастер проверяет вход по IMAP и SMTP и показывает понятную причину отказа. | авто |
| 1.3 | **[обяз.]** Пароль хранится в связке ключей ОС (Secret Service / Keychain / Credential Manager). В файлах настроек, базе, логах и сообщениях об ошибках пароля нет. | авто (grep по профилю), ручн. |
| 1.4 | **[обяз.]** Несколько учётных записей одновременно; удаление учётной записи стирает её кэш и пароль. | авто, ручн. |
| 1.5 | **[обяз.]** Логин может отличаться от адреса: `user@domain`, `DOMAIN\user`, `DOMAIN\user\shared` (общий ящик Exchange). Обратная косая черта передаётся без искажений. | авто, Exchange |

## 2. Шифрование и сертификаты

| № | Критерий | Проверка |
| --- | --- | --- |
| 2.1 | **[обяз.]** IMAP: TLS (993) и STARTTLS (143). SMTP: TLS (465) и STARTTLS (587). Сертификат проверяется по системному хранилищу. | авто, Exchange |
| 2.2 | **[обяз.]** Ошибка сертификата не принимается молча. Пользователь видит причину (истёк, не то имя, неизвестный издатель), срок действия и SHA-256 отпечаток. Может доверить **именно этот** сертификат для этой учётной записи; при смене сертификата вопрос задаётся снова. | авто (самоподписанный), Exchange |
| 2.3 | **[обяз.]** Если сервер не предлагает STARTTLS (например, receive-коннектор Exchange без сертификата), клиент не отправляет пароль открытым текстом. Пользователь видит объяснение «сервер не поддерживает шифрование». Незашифрованное подключение возможно только по явной галочке в настройках учётной записи, с предупреждением. | авто |
| 2.4 | **[обяз.]** Если сервер не предлагает поддерживаемый способ входа (например, только `GSSAPI NTLM`), клиент показывает предложенные механизмы. NTLM и Kerberos в 1.0 не реализуются. | авто |

## 3. Синхронизация (IMAP)

| № | Критерий | Проверка |
| --- | --- | --- |
| 3.1 | **[обяз.]** Список папок с вложенностью; русские имена отображаются корректно (modified UTF-7). | авто, Exchange |
| 3.2 | **[обяз.]** Роли папок определяются по SPECIAL-USE, а без него — по именам. Среди имён есть и имена Exchange: «Входящие», «Отправленные» / Sent Items, «Удаленные» / Deleted Items, «Черновики» / Drafts, «Нежелательная почта» / Junk Email, «Архив» / Archive. | авто, Exchange |
| 3.3 | **[обяз.]** Служебные папки Exchange без почты скрыты по умолчанию. Это Календарь, Контакты, Задачи, Заметки, Журнал, Проблемы синхронизации (с подпапками), Исходящие, RSS-каналы, Журнал бесед, а также английские аналоги. Ошибка в такой папке не ломает синхронизацию остальных. | авто, Exchange |
| 3.4 | **[обяз.]** Первая синхронизация папки с 50 000 письмами показывает последние 500 писем быстрее чем за 30 секунд; более старые подгружаются при прокрутке. | авто (генератор), Exchange |
| 3.5 | **[обяз.]** Новое письмо появляется в списке не позже чем через 60 секунд без ручного обновления: IMAP IDLE, без него — опрос раз в 2 минуты. IDLE перезапускается не реже раза в 25 минут: Exchange рвёт неактивные сессии. | авто, Exchange |
| 3.6 | **[обяз.]** Обрыв связи, `* BYE`, смена сети или сон ноутбука: клиент переподключается сам, ничего не дублирует и не теряет. | авто (kill контейнера), ручн. |
| 3.7 | **[обяз.]** Изменения, сделанные в другом клиенте (OWA, Outlook, телефон), — прочитано, флаг, перенос, удаление — видны после следующей синхронизации. | авто, Exchange |
| 3.8 | **[обяз.]** Смена UIDVALIDITY сбрасывает кэш папки и загружает его заново. Действие, поставленное в очередь до смены (флаг, перенос, удаление), к другим письмам с теми же UID не применяется. Флаг ставится заново на те же письма по Message-ID, перенос и удаление отклоняются с понятной ошибкой. То же для папки Exchange, кэш которой собран заново. | авто |
| 3.9 | **[обяз.]** На одну учётную запись не больше 3 одновременных IMAP-соединений (лимит Exchange — 16 на пользователя). | авто |
| 3.10 | **[обяз.]** После отказа во входе (неверный пароль, недоверенный сертификат, сервер без TLS) автоматические попытки прекращаются до действия пользователя. Повторы раз в несколько минут блокируют доменную учётную запись по политике AD. | авто |
| 3.11 | **[обяз.]** Действие, которое ждёт ответа сервера (открыть письмо не из кэша, отметить, перенести, «Готово», удалить, поиск на сервере), во время полной синхронизации ждёт недолго. Оно ждёт не дольше синхронизации одной папки или одной пачки офлайн-загрузки, а не всех папок. Синхронизация после него продолжается с оставшихся папок, ни одна не пропускается и не проходится дважды; задача «Синхронизация» одна на проход. Два действия подряд выполняются в порядке отправки. | авто (очередь воркера), ручн. |
| 3.12 | **[обяз.]** На «сервер занят» (`ErrorServerBusy`, троттлинг EWS) клиент не шлёт запросы раньше паузы `BackOffMilliseconds` из ответа. Без неё ждёт 5 секунд, удваивая паузу, пока сервер занят; пауза не больше 5 минут. Соединение не сбрасывается и вход не повторяется. Действие пользователя ждёт паузу до 5 секунд, при более длинной сразу получает «сервер занят, повторите через N с». Ящик не встаёт на паузу, синхронизация продолжается сама. | авто (скриптованный EWS, очередь воркера), Exchange |

## 4. Чтение

| № | Критерий | Проверка |
| --- | --- | --- |
| 4.1 | **[обяз.]** Общий входящий по всем учётным записям, отдельные папки, фильтры «непрочитанные» и «с флагом». | авто, ручн. |
| 4.2 | **[обяз.]** Кодировки UTF-8, Windows-1251, KOI8-R в теме, адресах, теле и именах вложений, в base64 и quoted-printable, отображаются без «кракозябр». | авто (фикстуры) |
| 4.3 | **[обяз.]** HTML показывается в изолированной области: скрипты, формы, iframe и обработчики событий вырезаются; ссылки открываются в системном браузере с показом настоящего адреса. | авто, ручн. |
| 4.4 | **[обяз.]** Удалённые картинки по умолчанию не грузятся, есть кнопка «показать» для письма и «всегда для отправителя». Подлинность отправителя решает лестница доказательств — тот, кто видел письмо целым. Ступень 1: сервер ящика написал `dmarc=pass` за организацию `From` — картинки и логотип. Ступень 2: тот же сервер написал прошедший `dkim=` или `spf=` за организацию `From` без `dmarc=` (Яндекс) — картинки и логотип. Своей проверки на этих серверах нет. Ступень 3: сервер молчал, а письмо пришло теми же байтами — своя проверка подписи DKIM — картинки и логотип. Ступень 4: Exchange в своей сети отдал письмо, собранное заново, — своя проверка подписи по исходным заголовкам письма (`0x007D`), без хэша тела — картинки, но без логотипа. Защита от повтора: подпись должна покрывать тот заголовок, в котором стоит один из адресов ящика (`To` или `Cc`) — основной адрес, псевдоним или плюс-адрес (`ящик+метка@`). Адреса эти Депеша спрашивает у Exchange, когда ящик подключается, и сверяет без учёта регистра; пока сервер их не назвал, сверяется адрес, под которым ящик заведён. Время письма (`t=` подписи или подписанный `Date`) должно быть близко к получению — предел сутки. Ступень 5: никто не подтвердил — картинок нет. `Authentication-Results` верится только от серверов, которые ставят свой заголовок сверху и вырезают чужие копии: Gmail, Яндекс и Mail.ru по IMAP, Exchange Online по EWS. Остальные отдают поддельный заголовок как пришёл: свой IMAP-сервер организации, Exchange в своей сети, Exchange Online по IMAP. Письмо с тем же `From` без подтверждения показывается без картинок. Встроенные (`cid:`) картинки показываются сразу. У ящика есть переключатель «доверять по адресу, если проверить нельзя» (выключен по умолчанию). Включённый доверяет адресу там, где проверить нельзя никак, и строка честно говорит, что адрес не проверен. Логотипа он не даёт никогда, и явное «нет» сервера (`dmarc=fail`, `dkim=fail`) не перебивает. | авто (корпус писем), ручн. |
| 4.5 | **[обяз.]** Вложения: список с размерами, сохранить, открыть системным приложением, сохранить все. С папкой для вложений (в настройках или у ящика) «Сохранить» и «Сохранить все» пишут в неё без диалога, не затирая файлы с тем же именем. «Сохранить как…» спрашивает место. Вложенные письма (`.eml`) показываются как вложения. Приглашение (`.ics` или часть `text/calendar`, в том числе в `multipart/alternative` без вложения) стоит карточкой встречи на месте строки этого файла, над телом письма. В карточке название без «Canceled:» и других слов почтовой программы, время в поясе человека, место и ссылка на видеовстречу. Ниже организатор, участники с ответами и повторение словами. Пояс организатора стоит рядом мелко, если он другой. «Добавить в календарь» отдаёт файл системному приложению, «Сохранить .ics» сохраняет его; кнопок ответа нет. Отмена (`METHOD:CANCEL` или `STATUS:CANCELLED`) — красная рамка, зачёркнутое время и «Отменена организатором». Обновление (тот же `UID` с большим `SEQUENCE`) — пометка «Изменено» и прежние значения рядом, когда более раннее письмо с этой встречей есть в базе. Несколько событий — первое карточкой и «Ещё N». Файл, который не разобрался, остаётся вложением, а карточка говорит почему. | авто, ручн. |
| 4.6 | **[обяз.]** Открытие письма не ставит «прочитано» до показа; «прочитано» и «флаг» переключаются вручную и уходят на сервер. | авто |
| 4.7 | **[обяз.]** Уже открытые письма читаются без сети. | ручн. |
| 4.8 | **[жел.]** `winmail.dat` (TNEF) раскрывается во вложения. | ручн. |
| 4.9 | **[жел.]** Группировка в цепочки по `References` / `In-Reply-To`. Место цепочки при сортировке по дате и дату в строке задаёт последнее входящее письмо: свой ответ цепочку не поднимает (в «Отправленных» — своё последнее письмо). Отправленный ответ появляется в цепочке без смены папки, в том числе на Exchange и Gmail, где копию кладёт сервер. | авто |
| 4.10 | **[жел.]** Вложения просматриваются внутри приложения, в области чтения на месте текста письма (список и строка вложений остаются видны, показанное вложение подсвечено). Оболочка одна для всех форматов: картинки, PDF, Word, таблицы, Markdown, HTML, CSV в любой из русских кодировок, текст, вложенные письма. Стрелки ←/→ переключают вложения, Esc закрывает; документы без скриптов и сети; неизвестный формат предлагается открыть в приложении. | авто |
| 4.11 | **[жел.]** Письмо открывается в отдельном окне двойным щелчком; ответ пишется в этом окне; «Готово» и удаление закрывают окно, отмена — в главном. Клавиши плагинов («h» — «Отложить», «w») работают и здесь: меню открывается у кнопки письма. Ctrl+K открывает палитру и в окне письма, но без команд списка, папок, поиска и настроек: «Ответить», «Переслать», «Печать» есть. | авто |
| 4.12 | **[жел.]** Письмо с частью `text/markdown` показывается с переключателем «HTML · Markdown · Текст» над текстом (в узком окне — выпадающий список). У остальных писем его нет, пока настройка не показала письмо не так, как прислал отправитель. Markdown рисует «Депеша»: заголовки, таблицы, код, цитаты, списки задач с неактивными галочками; очищается как HTML, внешние картинки — по тем же правилам. Markdown-часть — не вложение. Настройка «Почта» → «Чтение» → «Показывать письма»: как прислал отправитель (по умолчанию), предпочитать Markdown, предпочитать обычный текст. Выбор в письме действует, пока оно открыто. | авто |
| 4.13 | **[жел.]** Если в «Кому» и «Копии» вместе больше 10 получателей, шапка письма показывает их свёрнутыми. В каждой строке три первых по имени и «и ещё N», полный список — во всплывающей подсказке. «и ещё N» разворачивает обе строки, «Свернуть» в конце последней сворачивает (`aria-expanded`, с клавиатуры тоже); каждое письмо открывается свёрнутым. Короткие списки показываются целиком, как раньше; так же в отдельном окне письма и во вложенном письме (`.eml`) во встроенном просмотрщике. | авто, ручн. |
| 4.14 | **[жел.]** Текст письма любого вида (обычный текст, HTML, Markdown) лежит на одной карточке: рамка, скругление и отступы одинаковые, переключение «HTML · Markdown · Текст» меняет только содержимое. Обычный текст и Markdown — в цветах темы, смена темы перекрашивает их сразу; строка обычного текста не длиннее примерно 72 знаков. HTML остаётся на белом во всех темах: цвета письма задаёт отправитель. Так же выглядит вложенное письмо (`.eml`) во встроенном просмотрщике. | ручн. |
| 4.15 | **[жел.]** Письмо печатается отдельным листом, а не интерфейсом (#70). Печатать можно через `Ctrl+P` на открытом письме. Он работает в главном окне, в окне письма и из поля ввода, а также через палитру, «Ещё» и контекстное меню строки. В последнем случае печатается строка, по которой щёлкнули: правый щелчок, как и для остальных пунктов меню, выделяет её и открывает в читалке. Печатается одно открытое письмо, без цепочки. Шапка листа: тема, От, Кому, Копия, Дата, имена вложений; логотипа нет. Тело — в виде, выбранном на экране (HTML, Markdown или текст), внешние картинки — только если на экране показаны; лист всегда светлый. Печать — через системный диалог (PDF — из него), отдельной кнопки нет. Браузерная печать (`Ctrl+P`, на macOS `Cmd+P`) не срабатывает ни в одном окне, в том числе при написании письма и при переназначенной клавише «Печати». При написании письма не печатается ничего; на macOS `Ctrl+P` в поле — клавиша самого поля. Клавиши работают и при фокусе внутри тела письма. Тело письма лежит в своём блоке листа: его `position:absolute`/`fixed` не ложится поверх шапки. На macOS лист печатается из отдельного `WKWebView` (команда `print_sheet`): `window.print()` в `WKWebView` ничего не делает. | авто, ручн. |
| 4.16 | **[жел.]** Цепочка раскрывается прямо в списке (#179): счётчик писем у строки — кнопка, `→`/`←` на строке со счётчиком раскрывают и сворачивают её. Письма цепочки идут строкой с отступом, со своей датой и, если письмо не в открытой папке, своей папкой; значки плагинов — как у обычной строки. Выбранное письмо цепочки отмечено только фоном, без галочки. Курсор на письме цепочки показан полосой слева, а не фоном выбора. Так подсвечено ровно то, что посчитано. Архив или перенос письма, которое остаётся в цепочке, не убирает его строку: подпись папки сразу меняется. Письмо уходит, только если новая папка (Корзина, Спам) его в цепочку не берёт — так же, как в читалке. Раскрытие — локальное состояние строки, сбрасывается при перезагрузке и смене вида. Строка списка остаётся одним `role="option"`. | авто |
| 4.17 | **[жел.]** Цепочка читается аккордеоном (#180): по умолчанию раскрыто последнее по дате письмо, дальняя история свёрнута строкой «Ещё N писем» (сверху и снизу от раскрытого). Свёрнутые письма — строкой (отправитель, превью, дата, папка). Раскрытые письма — каждое со своей шапкой, как у открытого письма. У неё отправитель с адресом, «Кому», «Копия», отметки, дата, размер, ящик (4.6 пересмотрено). И своя линия кнопок «Ответить / Переслать / Удалить / … Ещё». Быстрый ответ и просмотр вложений остаются у одного открытого письма. Тема цепочки стоит один раз сверху, над всеми письмами. У раскрытого письма видны его вложения — имя, размер и кнопка сохранения. Открытие цепочки читает её целиком. | авто |

Принятый риск к 4.4 (0.8.13). DNS без DNSSEC. Ключ подписи и запись DMARC Депеша берёт из DNS без DNSSEC. Тот, кто подменяет ответы DNS в сети пользователя, может подтвердить поддельное письмо от доверенного отправителя. Тогда картинки письма загрузятся. Ущерб один: отправитель узнаёт, что письмо прочитано. Свою проверку Депеша делает на ступенях 3 и 4 — там, где сервер ящика не дал решения. Это свой IMAP-сервер организации, Exchange в своей сети и Exchange Online по IMAP. На ступени 2 (выровненная подпись сервера без DMARC) своей проверки нет. Сервер проверил хэш тела при приёме, и его слово — слово того, кто видел письмо.

Принятый риск к 4.4 (0.8.13): поддомен в `d=`. Подпись поддомена организации отправителя считается подписью отправителя (`d=mg.bank.ru` для `bank.ru`, нестрогое выравнивание DMARC): иначе не проходит обычная рассылка через сторонний сервис. Если организация отдала поддомен третьей стороне, та может подписать письмо от имени организации. Тогда она узнаёт, что письмо прочитано, а если в записи DMARC организации нет `adkim=s`, письмо получает и подтверждение отправителя.

Принятый риск к 4.4 (0.8.13): тело письма при проверке по заголовкам. На ступени 4 (Exchange в своей сети) подпись покрывает только заголовки письма: тело Exchange собрал заново, и проверить его нельзя. Тот, у кого есть настоящее подписанное письмо на этот же ящик, может подменить тело письма и узнать, что оно прочитано. Поэтому на этой ступени нет логотипа: знак подлинности должен стоять на полной проверке.

Принятый риск к 4.4 (0.8.13): переключатель «доверять по адресу». Включённый, он доверяет адресу доверенного отправителя там, где проверить нельзя никак: сервер ящика молчит, письмо не подписано, а своего сервера-посредника у Депеши нет. Подделка адреса тогда тоже получает картинки доверенного отправителя, и отправитель узнаёт, что письмо прочитано. Переключатель выключен по умолчанию, логотипа он не даёт никогда, а явное «нет» сервера (`dmarc=fail`, `dkim=fail`) не перебивает.

## Проверка отправителя перед меткой (0.8.13)

Перед меткой выпуска оператор открывает по одному письму каждой строки на своих ящиках и сверяет строку над письмом с ожиданием. В журнале (`debug`) на каждое письмо одна строка `sender check` — по ней видно ящик, ступень, ответ сервера и итог своей проверки. Адресов людей в строке нет: домены и селекторы можно.

| № | Ящик | Письмо | Ожидание: ступень | Ожидание: картинки | Ожидание: логотип | Что смотреть в журнале |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | Gmail | письмо доверенного отправителя | 1 (`dmarc=pass` сервера) | есть | есть | `step="1" verdict="confirmed"` |
| 2 | Яндекс | письмо доверенного отправителя | 2 (`dkim=pass` без `dmarc=`) | есть | есть, если у домена есть запись BIMI | `step="2" verdict="confirmed"` |
| 3 | Яндекс | подделка под доверенного отправителя без подписи | — | нет | нет | `step="-" verdict="unconfirmed" outcome="unsigned"` |
| 4 | Mail.ru | письмо доверенного отправителя | 1 (`dmarc=pass` сервера) | есть | есть | `step="1" verdict="confirmed"` |
| 5 | Exchange Online | письмо доверенного отправителя | 1 (`dmarc=pass` сервера) | есть | есть | `step="1" verdict="confirmed"` |
| 6 | Exchange в своей сети | письмо доверенного отправителя с подписью, адресованное основному адресу ящика, псевдониму или плюс-адресу (`ящик+метка@`) | 4 (подпись по исходным заголовкам) | есть | нет | `step="4" verdict="confirmed" own=headers:pass` и `mailbox=` со всеми адресами ящика, которые Exchange назвал |
| 6.1 | Exchange в своей сети | подпись доверенного отправителя, а письмо пришло на чужую рассылку (адреса ящика в `To` нет) | — | нет | нет | `step="-" verdict="unconfirmed" outcome="no_recipient_in_h"` и `mailbox=` со всеми адресами ящика |
| 7 | Exchange в своей сети | письмо коллеги по организации | внутренняя почта | есть | нет | `step="internal" verdict="confirmed"` |
| 8 | Exchange в своей сети | подделка под доверенного отправителя без подписи | — | нет | нет | `step="-" verdict="unconfirmed" outcome="unsigned"` |
| 9 | свой IMAP | письмо доверенного отправителя с подписью | 3 (своя полная проверка) | есть | есть | `step="3" verdict="confirmed" own=full:pass` |
| 10 | свой IMAP | письмо без подписи | — | нет | нет | `step="-" verdict="unconfirmed" outcome="unsigned"` |
| 11 | свой IMAP, переключатель «доверять по адресу» включён | письмо без подписи от доверенного адреса | по адресу | есть | нет | `step="address" verdict="confirmed"` |
| 12 | свой IMAP, переключатель включён | подделка под доверенного адреса | по адресу | есть | нет | `step="address" verdict="confirmed"` |
| 13 | любой, где сервер написал `dmarc=fail` | подделка под доверенного адреса | — | нет | нет | `step="-" verdict="unconfirmed"` и `server=dmarc=fail`; переключатель «по адресу» не перебивает |

Строка журнала выглядит так: `sender check id=… kind=… folder=… from_domain=… listed=… step="…" verdict="…" server=… own=… outcome="…" sig=d=…,s=…,a=…,x=…,l=…,from_in_h=… mailbox=…`. Адресов людей в ней нет: домены и селекторы можно. `mailbox` — адреса самого проверяемого ящика, которые сверялись на ступени 4 (основной, псевдонимы), то есть адреса оператора, а не чужих людей; пустой список читается как `-`.

`outcome` — итог своей проверки:

- `pass` — подпись стоит.
- `unsigned` — подписи в письме нет.
- `body_hash` — тело письма не то, что подписано.
- `bad_signature` — подпись не сходится с заголовками.
- `expired` — подпись истекла (`x=`).
- `no_key` — ключа нет, или DNS не ответил.
- `testing_key` — ключ в режиме проверки (`t=y`).
- `auid` — `i=` чужого домена.
- `sha1` — подпись посчитана SHA-1.
- `no_from_in_h` — подпись не покрывает `From`.
- `l_refused` — подпись с длиной тела (`l=`).
- `too_many_h` — подпись покрывает слишком много заголовков.
- `from_mismatch` — подпись чужой организации.
- `strict_policy` — `adkim=s` требует точного имени.
- `replay` — письмо не от того времени, что получено.

Строки 1–10 повторяют таблицу корпуса писем (`crates/depesha-core/tests/sender/table.json`): то, что автотест проверяет на обезличенных заголовках, оператор проверяет на своих живых письмах.

## Сценарий ручной приёмки на Exchange 2019

Нужен тестовый ящик на Exchange 2019 с включённым IMAP4 и SMTP-submission. Предусловия на сервере: запущены службы `MSExchangeIMAP4` и `MSExchangeIMAP4BE`; у ящика `ImapEnabled = True`; на receive-коннекторе `Client Frontend` назначен сертификат, то есть STARTTLS есть.

1. Добавить ящик мастером: адрес → автоопределение → вход. Ожидание: найден `mail.<домен>`, 993 TLS и 587 STARTTLS, вход успешен. (1.1, 1.2, 2.1)
2. Повторить с логином `ДОМЕН\пользователь`. (1.5)
3. Проверить папки: русские имена, роли, служебные папки скрыты. (3.1–3.3)
4. Отправить из OWA три письма: UTF-8, Windows-1251, с вложением и картинкой в теле. Ожидание: появляются без ручного обновления меньше чем за минуту, читаются корректно. (3.5, 4.2–4.5)
5. В OWA пометить письмо прочитанным и перенести другое в папку. Ожидание: изменения видны в Депеше. (3.7)
6. Ответить, ответить всем, переслать с вложением. Ожидание: письма доставлены, в OWA цепочка собрана, копия в «Отправленных» одна. (5.1, 5.3)
7. Отправить 7 писем подряд. Ожидание: после пятого `421 4.4.2`, оставшиеся уходят автоматически. (5.4)
8. Отправить от чужого адреса. Ожидание: понятная ошибка про права, письмо не потеряно. (5.4, 5.5)
9. Удалить письмо, затем удалить его из «Удаленных». (6.1)
10. Оставить клиент на 40 минут, затем отправить письмо из OWA. Ожидание: письмо появилось без перезапуска. (3.5, 3.6)
11. Отключить сеть на 2 минуты и включить. Ожидание: синхронизация восстановилась сама. (3.6)
12. Если сервер отдаёт просроченный или самоподписанный сертификат: понятное предупреждение и доверие конкретному отпечатку. (2.2)
13. Найти поиском на сервере письмо старше 500 последних. (6.5)
14. Ответить, ответить всем и переслать три письма из Депеши. Ожидание: значки сразу; в OWA у писем те же отметки (ответ, ответ всем, пересылка). Ответить всем в OWA на четвёртое: после синхронизации в Депеше значок «ответ всем» с подсказкой «отметка сервера, время неизвестно». (6.7)
15. Включить «Убирать письмо из входящих, пока не ответят» и ответить на письмо из «Входящих». Ожидание: через 10 секунд цепочка в папке «Ждут ответа», в OWA тоже; «Оставить во входящих» возвращает её. Ответить ещё раз и написать ответ из OWA другого ящика: письмо вернулось во «Входящие» с меткой «пришёл ответ», автоответ «Нет на месте» его не возвращает. (6.8)

## Сценарий ручной приёмки: Exchange 2019 только с OWA (EWS)

Нужен ящик на Exchange 2019, у которого снаружи опубликованы OWA и `/EWS/Exchange.asmx`, а IMAP и SMTP закрыты. На виртуальном каталоге EWS включена Basic-авторизация (`Get-WebServicesVirtualDirectory | fl BasicAuthentication`).

1. Мастер → «Exchange без IMAP (только OWA)…» → адрес, `ДОМЕН\пользователь`, пароль, поле сервера пустое. Ожидание: адрес EWS найден через Autodiscover, вход успешен.
2. Повторить, указав в поле сервера адрес OWA `https://mail.<домен>/owa`. Ожидание: подставлен `https://mail.<домен>/EWS/Exchange.asmx`.
3. Неверный пароль. Ожидание: «неверный логин или пароль», ящик на паузе, повторных попыток нет.
4. Папки: «Входящие» с подпапками, «Отправленные», «Удаленные», «Нежелательная почта» с ролями; календарь, контакты, задачи и «Исходящие» скрыты.
5. Письмо из OWA появляется меньше чем за минуту без ручного обновления; прочтение и перенос в OWA видны в Депеше после синхронизации.
6. «Загрузить старые» в папке с больше чем 500 письмами догружает следующие 200.
7. Ответить, переслать с вложением, отправить со скрытой копией. Ожидание: письма доставлены, получатель Bcc получил письмо, копия в «Отправленных» одна (её кладёт сервер).
8. Отложить письмо до времени через 2 минуты. Ожидание: вернулось во «Входящие» непрочитанным.
9. Удалить письмо, затем удалить его из «Удаленных».
10. Поиск на сервере находит письмо старше загруженного окна.
11. Если Basic на EWS выключен: понятная ошибка с командой для администратора.

## Сценарий ручной приёмки: вход через Google, Яндекс и Microsoft

Нужна сборка с OAuth-клиентами (переменные `DEPESHA_*_CLIENT_ID`) или клиенты, указанные в настройках.

1. «Войти через Google» → в браузере войти и разрешить доступ. Ожидание: вкладка пишет «Вход выполнен», ящик добавлен и синхронизируется, отправка работает, копия в «Отправленных» одна.
2. То же для Яндекса — в настройках Яндекс Почты должен быть включён IMAP с авторизацией по OAuth-токенам. То же для Microsoft: Outlook.com или Microsoft 365 с разрешённой авторизацией SMTP.
3. Отозвать доступ приложения в настройках аккаунта провайдера. Ожидание: ящик на паузе с ошибкой «войдите заново»; «Исправить» → «Войти заново» возвращает работу без удаления ящика.
4. Закрыть вкладку браузера, не входя. Ожидание: «Отмена» в мастере прерывает ожидание; кнопки других провайдеров всё это время доступны, щелчок по одной из них прерывает ожидание и открывает её вход. После отмены или ошибки строка «Ждём ответа … из браузера…» пропадает, повторный вход тем же провайдером работает.
5. Перезапустить Депешу. Ожидание: повторный вход не нужен, токен обновляется сам.
6. «Войти через Google» и на странице разрешений не отметить доступ к Gmail. Ожидание: мастер сразу пишет «Google не дал доступ к почте…», ящик не сохраняется.
7. Сборка без клиента какого-то провайдера. Ожидание: кнопки этого провайдера в мастере нет; без единого клиента блока входа через браузер нет вовсе.

Google-клиент для сборки: в Google Auth Platform создать клиент типа Desktop app. В Data access добавить `https://mail.google.com/` (restricted), `openid`, `.../auth/userinfo.email`, `.../auth/userinfo.profile`. Пока приложение в режиме Testing, адрес должен быть в Test users, а токены живут 7 дней. Google спрашивает согласие на каждый scope отдельно: на странице разрешений доступ к Gmail надо отметить.
